# Decisions

Numbered, in the order they were taken. Each has the context, the choice, why, and what it costs.
The plain-words version of the big ones is in `docs/LITEPAPER.md`. Add to the end; do not renumber.

| # | Context | Choice | Why | Cost |
|---|---|---|---|---|
| 1 | The first plan's name, Jokko, is already a known hub in Dakar (Jokkolabs). A second idea, Weccit, is too close to the money app Wecci Ma | Melax, Wolof for lightning | Checked in the Wolof New Testament (Matthew 24:27). No wallet or fintech found under that name | A graphics developer and a US health-data firm share the word. Different fields |
| 2 | Server code needs to run in Docker and on a Windows laptop with no surprises | Node 24 runs the TypeScript sources directly. No compile step for the server | One less place for the running code to differ from the code under test | Only erasable TypeScript syntax: no `enum`, no parameter properties. Imports carry the `.ts` extension |
| 3 | TypeScript 7 is out, typescript-eslint 8.72 refuses it | Pin TypeScript 6.0.x | Lint and type check must use the same compiler | Slower type check than the new compiler |
| 4 | The plan named Drizzle as the database layer | Plain SQL behind a small `Db` interface, on `pg` in production and PGlite in tests | Every money movement is one readable statement. The same SQL runs in-process, so ledger tests need no server | No typed queries. Migrations are written by hand |
| 5 | A balance could be a column | Double-entry journal with a hash chain, idempotency keys and a rule that only `ext:` accounts go negative | History can be verified and a replayed request cannot pay twice | Every posting takes one lock. One writer at a time |
| 6 | PIN hashing library | `crypto.argon2` built into Node, with the server pepper as Argon2's secret input | No native add-on to build in Docker. The pepper never reaches the database | Needs Node 24.7 or later |
| 7 | Voucher codes need a check character. ISO 7064 hybrid mod 31,30 was the first pick | Damm's scheme over a 30-element quasigroup (order 3 times Damm's order-10 table) | Measured: the ISO scheme missed 60 of 26,100 neighbour swaps. Damm's misses none, proven by enumeration in the test | A lookup table that needs a comment |
| 8 | The plan asked for a 16-character code with 79 bits and a checksum. Both cannot hold | 15 random characters plus one check character: 73.6 bits, then scrypt (N = 2^15) | Catching typos matters more on a keypad than five bits | Slightly smaller search space |
| 9 | The gateway needs hold invoices and description-hash invoices, and something must play the outside world | Three LND nodes on regtest: world, gateway, mint | With two, the gateway would have had to share the mint's node, which breaks the separation the design rests on | About 150 MB more memory |
| 10 | Lightning backends differ | One `LightningBackend` interface, one contract suite run against every implementation | The suite found a real difference: the NWC sandbox cannot cancel an unpaid hold invoice | `cancel` returns a boolean and callers must handle both answers |
| 11 | The Cashu library can prepare and persist its own previews | Build the outputs ourselves, store them as a plain plan, call the mint's endpoints, recover with the mint's restore endpoint | Recovery depends only on the Cashu protocol, not on library internals. The plan is plain JSON, easy to seal and store | We own a little more code around the library |
| 12 | The library skips the swap when inputs already add up to the amount | Always swap | Two owners must never hold the same secret | One mint round trip per transfer |
| 13 | Tests for money paths could use a stand-in mint | Run them against real Nutshell and real LND on regtest. Inject faults at the network edge of the test | A stand-in agrees with whatever its author believes. The real mint showed cached replies, automatic retries and witness formats | Needs Docker. Minutes, not seconds |
| 14 | A lost reply could be retried | Store the plan first, then ask what happened. Never retry an unknown outcome | Retrying is how money gets paid twice | "Pending" is a state users can see. One outgoing operation per owner at a time |
| 15 | Deposits may cost a routing fee from the gateway to the mint | The user is credited the full amount. The operator books the fee as a cost | "Sent 5,000, received 5,000" is what people expect. Over a direct channel the fee is zero | The operator pays when the route is longer |
| 16 | Pay-out fees | The user pays the real fee. The vault refuses if the mint's reserve is above 5 sats or 0.5 % | No surprise fees | Measured: with no known route the mint asks 1 % and pay-outs of 1,000 sats or more are refused. To revisit in phase 8 |
| 17 | The PIN could be the encryption key for a user's proofs | The PIN is a gate only. Proofs are sealed with a key from the server pepper and a per-owner salt | A five-digit PIN can be tried exhaustively. Calling it encryption would be false | The operator can read proofs. Stated openly |
| 18 | SMS can carry commands | Inbound commands can check, redeem, report, cancel and approve. None can send money out | Sender numbers can be spoofed | Sending money always needs a USSD session |
| 19 | Users type names and comments with accents | Our own wording is GSM-7 only and refused otherwise. User text is folded or replaced | One accent outside GSM-7 turns a 160-character SMS into 70-character parts | French without ç, ê, ô. Wolof without ë and ŋ |
| 20 | Limits could be in sats | Limits and screens are in FCFA, storage in sats | People and regulators here count in francs | The rate can move between screen and payment. Rounding up to one franc |
| 21 | The work was planned as parallel work packages | Numbered phases, one at a time, stop after each, plan file updated every time | The owner's call on 15 Nov 2026. It keeps the work reviewable and lets someone else pick it up | Slower than running in parallel |
| 22 | After the stack sits stopped, LND will not start: the chain looks stale. And the block miner waited for LND | The regtest helper mines a block before waiting for the nodes, keeps mining while they sync, and reconnects peers by host name on every run | Found on 15 Nov after a night stopped. A judge restarting the demo would have hit it | None |
| 23 | A user's balance could be a number in a table, as in mobile money. This was settled in the first plan and is recorded here because everything rests on it | Balances are Cashu ecash proofs issued by a separate mint | The party that can issue money knows no one, and the party that knows people cannot issue. Vouchers are real bearer notes. Users can leave with a standard token | Far more code than a table, a mint round trip per transfer, and a second party to trust |
| 24 | The wallet menus could be handlers that read input and call services as they go | One pure machine: state in, a screen or an effect out. A dial string is a queue of pre-typed inputs, and the queue is dropped at every code prompt | Every path replays as text, in three languages, with no network. The only places a code can exist are a short list of steps a test walks | A code can never be part of a dial string, so there is no one-shot "dial and it is paid" |
| 25 | Balance and history could open straight from the menu | Both ask for the code. Limits, the address and the language do not | A phone gets lent or picked up, and what is in the account is private | One more step for the most used screen |
| 26 | The rate can move between the confirm screen and the code | The sats shown on the confirm screen are the sats sent. The wallet refuses if they are more than 5 % from the current rate | What the user agreed to is what moves. Between two users nobody is exposed to the rate | A quote can be about five minutes old when a dropped session is picked up |
| 27 | History rows and SMS could be written after a send returns | They are written by the vault's settle hook, inside the transaction that settles the ecash, under one receipt number. An SMS whose text cannot be built is logged and skipped | No moment where money moved and the receipt does not exist, also when recovery finishes a send hours later. A broken sentence must not leave money locked | In that rare case money moves with no SMS. The settle hook has one owner (`SettleRouter`) that every later flow must go through |
| 28 | Two sessions of one user can both pass a limit check before either sends | One send at a time per user, queued in the gateway's memory, and the limits are checked again after the code | Proven with two sessions typing the code at the same moment | One gateway process only. Sessions are in memory for the same reason. Both move to the database before any scaling out |
| 29 | One server pepper could key everything | Three keys derived from it by label: code hashing, phone lookups, sealed columns. The vault keeps deriving one key per owner from the pepper and a salt | The same bytes never serve two purposes | Changing a label orphans every account. Losing the pepper still loses everything |
| 30 | A send could look up an earlier operation, the limits or the freeze before checking the code | The code comes first, always. "Frozen" is only said to someone who typed the right code | Someone holding the phone learns nothing without the code, not even that the account is frozen | A replayed request pays for one more slow hash |
| 31 | An SMS from an unknown number could get a "dial to open an account" reply | It gets nothing. An account gets at most five replies in ten minutes, and a message id is answered once | A sender number can be forged. Without this the server texts whoever an attacker names | Someone who texts SOLDE before opening an account hears nothing |
| 32 | Africa's Talking does not sign its callbacks | The route is a secret path plus an address allow-list. A wrong secret gets the same 404 as a path that does not exist. Outside demo mode the server will not start with the secret set and no allow-list | Nothing tells a prober that the route is there | Behind a proxy the allow-list depends on the proxy passing the caller's address. Not tested on a deployment yet |
| 33 | An amount refused by a limit or the balance | Before the code, the screen says why and asks for another amount. After the code, it says why and ends | Before the code a retry is harmless. After it, a session that keeps asking is a session someone can keep guessing in | The user redials after a late refusal |
| 34 | SMS texts could stay in the outbox table | The text is sealed while queued and deleted once a real send succeeded. Demo mode keeps it so the simulator can show it | A text can hold a voucher code | No way to re-read what was sent, outside demo mode |
| 35 | Demo conveniences could be switches a deployment forgets | One flag, `MELAX_DEMO`. With it the simulator route exists and SMS may stay in memory. Without it the route is absent and the server refuses to start unless a real SMS adapter is configured | The unauthenticated route and the "receipt" that never leaves are the two things that must not reach production by accident | Every test of non-demo behaviour has to name a real adapter |
| 36 | The menu tests passed the first time they ran, so I never saw them fail | French transcripts written by hand before the code, golden files for all three languages, and a script that breaks nine guarded lines one at a time to prove a test notices | A test that has never failed has not shown it can | The golden files must be re-read whenever wording changes |
| 37 | Gateway tests on PGlite only would leave real concurrency untested | The same tests run on a real Postgres server when `TEST_DATABASE_URL` is set | Row locks and the wrong-try counter only mean something with real connections. Both runs passed | A second database to create, and a second run before a phase ends |
| 38 | The demo needs accounts with money in them. One line could write a balance | The top-up is a real payment on the test network: the node that plays everybody else pays the gateway's node, then the wallet buys ecash. The seed uses the same path | No number in the demo that the real system could not have produced. The same function serves Lightning addresses in phase 8 | The demo gateway holds that second node's credentials, so the top-up exists on regtest only. Money flows one way, so channels have to be topped up (defect 29) |
| 39 | A deposit could be told how much arrived | `Wallet.deposit` is given a user and a payment hash. It asks the gateway's own node, credits the amount the node reports, and only for a settled invoice. The hash is the key of both the ledger entry and the vault operation | The caller is not believed. One payment is credited once, to one user | One more call to the node per deposit |
| 40 | The gateway image runs as an unprivileged user and cannot read the nodes' volumes, which belong to root | The regtest helper copies two nodes' certificates and macaroons into a volume the gateway mounts read-only: its own node and the world node. Never the mint's | The gateway stays unprivileged, and still cannot reach the mint's node | On regtest the gateway can spend from the world node. That node does not exist on a public network |
| 41 | The pages could be served by a static-file plugin | Files are read once at start into a map from URL to bytes. A request is answered from the map or gets the usual 404 | No request path reaches the disk, so there is nothing to climb out of. Fifteen hostile paths are tested | A new page needs a restart. One folder only: a later front end joins it or gets a second mount |
| 42 | The front end could use a framework | Plain TypeScript and CSS, built with Vite. No web fonts, nothing from another server | 13 and 17 KB per page, and it works with no internet. The script policy can then say "this server only" | More hand-written DOM code |
| 43 | A guide could tick a step when the visitor presses "next" | A step is ticked when the SMS outbox shows it happened, and the next opens only then | What the page says is what the wallet did | The page polls every 1.5 s. The guide depends on the `kind` of four SMS (rule 60) |
| 44 | The demo could use the live exchange rate | A fixed 40,000,000 F per bitcoin, set in `compose.yaml` and marked as a demo value. An empty variable gives the live rate | Works offline, and 500 F is always 1,250 sats, on the page and in the tests | Not the real price. The page says the rate is fixed |
| 45 | The server will not start without its secret, and a judge should not have to make one | A demo secret is written in `compose.yaml`, in the open, with a comment | One command, nothing to set | Anyone can open that demo database. It holds test money and made-up numbers |
| 46 | A visitor could be handed a seeded account | A visitor gets a fresh random number, kept in their browser, and opens their own account. A link offers a ready account for those in a hurry | Opening the account is the first thing a real user does, so it is the first thing shown | The demo database grows with every visitor |
| 47 | On a touch screen, focusing the typing line opens the system keyboard over the phone's keys | The line is only focused where there is a mouse, or when the visitor presses "abc" to type a name | The drawn keys stay usable with one thumb | Letters need one extra press |
| 48 | The Wolof on the pages is mine and unread, like the menus | Ship it, and say so on the page, in Wolof | A Wolof speaker should not have to wonder whether the mistakes are theirs | A visible admission on the first screen |
| 49 | When the world node runs out, the mint's node could pay it back | The helper opens another channel. The mint's node is never drained | The sats on the mint's side back ecash that people hold | Channels pile up on a long-lived test network |
| 50 | Browser tests could run against a dev server | They run against the `app` container | That is what a judge starts | The image has to be rebuilt before the browser tests whenever the gateway or the pages change (rule 66) |
| 51 | The plan put the agent escrow engine in its own app | It will be a module inside the gateway (phase 6) | The gateway has to stay one process until sessions and the send queue move to the database (rule 52). A second process that moves money would break that | `apps/gateway` grows |
| 52 | A held payment dies when its block delta runs out. LND's default of 80 blocks held one for 65 blocks, 32.5 minutes on our 30 s chain (`scripts/probe/hold-cltv-probe.ts`) | The hold invoice carries `ESCROW_CLTV_BLOCKS`. With `ESCROW_BLOCK_SECONDS` it must cover the 3 hour cap plus 22 blocks, or the gateway refuses to start. 432 on the stack, 80 on bitcoin | 432 held a payment 414 blocks, past the 360 the cap needs. A wrong pair of settings now stops the server instead of failing a trade at minute 33 | The agent's sats can be tied up in the route for up to 3 h 27 min on regtest. A payer refuses a delta that is too large: the world node did not pay at 2,100 |
| 53 | A cash-out's pay-out costs a Lightning fee, and someone has to carry it. The other road: the agent gets the sats less the fee | The user locks the sats plus `feeCapSat` of them. The agent's invoice is for exactly the sats agreed. What the fee does not use goes back to the user | The agent agreed to a number of sats for their francs and gets that number. The user sees the full amount locked before typing the code | A cash-out needs a little more balance than the sats shown. The confirm screen shows the locked amount, not the sats |
| 54 | A first cash-out with an agent is a spend to someone the user never paid. The other road: agents are exempt from the first-payment cap | The cap applies: 10,000 F at the first level | A thief with the phone and the code could cash out through a colluding agent as easily as send to a friend | A new user's first cash-out above 10,000 F is refused. Two smaller ones work |
| 55 | Either side may want out of a trade | A user can cancel a cash-in. Nobody can cancel a cash-out once it locked: the agent can decline before marking it sent, and the clock refunds after 45 minutes | During a cash-out the agent may be sending francs at that very moment. A user who could cancel then would keep both | A user who changes their mind waits up to 45 minutes |
| 56 | The user may get the francs before the agent marks them sent | The user can confirm from "locked" as well as from "sent" | What matters is that the francs arrived, and only the user knows that | None found |
| 57 | Disputes need someone to decide | A user opens one from the menu, with no code. Only `Escrow.decide` closes one, reached through `/ops/escrow/decide` behind `OPERATOR_SECRET`, or `/sim/decide` in demo mode. A disputed cash-out waits for the arbiter however long it takes | Opening a dispute moves no money. Deciding one does, so it sits behind a secret and leaves an `audit_log` row | A disputed cash-out keeps the user's sats locked until somebody decides. There is no console yet (phase 11) and no signature on the decision (phase 10) |
| 58 | An agent confirms a cash-in, and the held payment is gone before the engine settles it (the node let go, or it was cancelled) | The trade goes from "settling" to "bonding": the user is paid from the agent's bond | The agent said the francs arrived. The agent also has their sats back. The bond is there for exactly this | A slow engine costs the agent their bond for that trade, not the user |
| 59 | Gap 2 of phase 5: a mint payment that fails for good leaves the sats on the gateway's node | For a cash-in the credit is asked again under a new key, `cashin:<id>:credit:<n>`, with a wait that doubles from 30 s to 10 minutes | The trade row remembers who the sats belong to, so a second try cannot credit the wrong person | Deposits through the top-up button still have the gap. Phase 8 closes it for them |
| 60 | What counts against an agent's bond | Every cash-in not closed: open, held, settling, disputed, released and bonding | A released dispute is exactly the case the bond pays, so it must still lean on the bond until decided | An agent with one long dispute can take fewer new cash-ins |
| 61 | Where the agent desk goes in the menu | Entry 4 of the second page, shown only when the account is an agent's | The first page is the same for everybody, and 4 there is "pay a shop" | An agent presses 0 then 4 |
| 62 | Taking a bond back | All of it at once, refused while any trade of the agent is open, and the offer is paused in the same transaction | A cash-in cannot start against a bond that is on its way out | No partial withdrawal |
| 63 | People need to name a trade on the phone and in a dispute | A reference of D (cash-in) or R (cash-out) and five hex characters. Nobody types one: the desk shows the oldest trade waiting | Short enough for an SMS and a phone call to the arbiter | 1,048,576 references per kind. A clash is drawn again |
| 64 | The agent list must fit one USSD screen in the worst case | Three agents at most, names cut at 9 characters | With three 16-letter names, "Orange Money" and nine-digit sats the screen was 161 characters | Long names are cut on that one screen |
| 65 | On the demo page, a cash-in needs the second phone to be an agent's | Picking an agent on the second phone folds the four steps away and shows the agent's two steps instead. Picking anyone else brings them back | Two "do this now" steps at once were confusing in the stills | The four steps are out of sight while an agent holds the second phone |
| 66 | The agent's wallet on regtest | The demo's world node, the same one that pays top-ups. A real agent links a wallet by NWC, sealed under its own purpose | Both are a `LightningBackend`, so the engine does not know which it has | Only the Lightning leg was tested on the NWC sandbox. The sandbox cannot pay our regtest mint |
| 67 | Nutshell 0.22.1's watchdog stops the mint on a normal deposit when its once-a-minute check lands between the payment of a quote and the collection of the ecash (defect 52). The setting that stops this also stops the shutdown when issued ecash passes the node's balance | On the regtest mint, `MINT_WATCHDOG_IGNORE_MISMATCH=True`: every mismatch is still logged, and readings are still stored | A mint that stops in the middle of a demo or a test run, and stays stopped, protects nothing on a test network | This mint no longer stops itself when it has issued more than it holds. Phase 10's reserve check (ours, from outside) has to cover that, and it has to count paid quotes not yet collected. A real deployment needs the question answered again: a newer Nutshell, or a watchdog that knows about paid quotes |
